## Glossary

**EvidenceChain** — the core accumulator. Collects weighted `EvidenceItem` signals until `total_weight` crosses a confidence tier threshold. Caps (ceilings) can prevent a chain from reaching a tier even when weight is sufficient. Never compare raw `total_weight` directly — use `chain.confidence` or `confidence_meets()`.

**Confidence** — three tiers: `TENTATIVE` (single signal, manual verification needed), `FIRM` (multiple signals, reportable with caveats), `CONFIRMED` (exploit-grade proof, fully reportable). Defined in `models.py`.

**Cap / Ceiling** — an upper limit applied to an `EvidenceChain` via `chain.cap(level, reason)`. When a cap is active, `chain.confidence` is `min(accumulated tier, cap)`. Caps implement the doctrine gates below. See `models.py:EvidenceChain.cap()`.

**Doctrine Gate** — a named invariant (I1–I5) that mandates a specific cap in specific conditions. Enforced structurally inside validators, not by post-hoc weight adjustments.

**Signal** — a single observation (e.g., "sqlmap identified injection point") added to a chain via `chain.add(signal, source, weight)`. Positive weight moves toward CONFIRMED; no negative weights — instead use `chain.add_fp_check()` to record why a finding may be a FP.

**FP Check** — evidence that the finding may be a false positive, recorded via `chain.add_fp_check(reason)`. When the first FP check is added, the chain is capped at TENTATIVE and `chain.is_false_positive` becomes `True`.

**Calibration** — the feedback loop that compares predicted confidence against user acceptance/rejection and adjusts per-tool signal weights and per-vuln acceptance rates. Lives in `calibration.py`. Does NOT auto-apply — produces recommendations for human review.

**Pattern Analyzer** — classifies tools as elite/reliable/noisy/broken based on precision and FP rate across sessions. Feeds the calibration loop. Lives in `pattern_analyzer.py`.

**Learnings Store** — append-only JSONL at `~/.kambo/learnings.jsonl`. Cross-session memory. Entries decay in confidence over time (1 point per 30 days). Searchable by keyword, type, and minimum confidence.

**Evidence-Grade Doctrine** — the set of invariants (I1–I5) that prevent inflated confidence. See "Doctrine" section below.

**Pentest-Only Lock** — tools in the `ad_*` and `post_*` families are locked unless `Context.PENTEST` or `Context.CTF` is active. Enforced by the `@pentest_only` decorator in `scope.py`. Bug bounty context never unlocks them.

**Category-7 Gate** — info/infra/version-disclosure and exposed-credential findings submitted without a PoC are down-ranked (acceptance × 0.2) in `bounty_pricing.py` and receive a readiness-blocker. A working PoC lifts the gate.

**Canary** — an orthogonal marker used in SSTI/injection testing to avoid false positives from template engine defaults. Generated by `make_arithmetic_canary()` in `canary.py`. Orthogonality checked by `is_orthogonal_marker()`.

**Baseline Differential** — proof of causality: the injected marker is present in the payload response and absent from a structurally-similar control request. Required for CONFIRMED on single-response reflexive classes (doctrine I1).

**OOB Hit** — an out-of-band callback (DNS ping, HTTP request to Interactsh/Burp Collaborator) received after sending a payload. Proves execution for blind classes (SSRF, RCE, XXE). Required for CONFIRMED on blind classes when no inline evidence is present (doctrine I3).

**Platform Tool** — tools in `platforms.py` that interact with HackerOne/Bugcrowd APIs. Require `HACKERONE_API_USER`/`HACKERONE_API_TOKEN` from the repo-root `.env` (loaded at startup by `env_loader.py`).

## Evidence-Grade Doctrine

These invariants are enforced structurally in `validation.py` via `chain.cap()`. They are NOT advisory — violating them is a bug.

**I1 — Causality or nothing (reflexive classes)**
A reflexive finding (XSS, SQLi, SSTI, RCE, XXE, deserialization, prototype pollution) cannot reach CONFIRMED from a single response. CONFIRMED requires either:
- a baseline differential (payload response differs from control), or
- a correlated OOB hit for blind classes.
Implementation: `cap_single_response_reflexive()` in `validation.py`.

**I2 — Orthogonal markers only (SSTI)**
SSTI payloads must use arithmetic canaries that produce non-trivial, non-dictionary results (e.g., `{{31337*1337}}→41897569`). The classic `{{7*7}}→49` is banned — too many template engines echo numeric literals. Checked by `is_orthogonal_marker()`.

**I3 — OOB body keywords are reflection, not execution (blind classes)**
Finding the OOB token in a response *body* proves only reflection, not execution. Only a *received OOB callback* (DNS lookup, HTTP ping to collaborator) proves causality for blind classes (SSRF, blind SQLi, blind RCE). The body-token branch is explicitly skipped when `oob_hit=True` to prevent double-counting.

**I4 — Context-aware XSS gating**
XSS reflection in non-executable contexts (HTML comments, `<script type="application/json">` blocks) caps at TENTATIVE — JavaScript engines will not execute such content. Curl-only reflection caps at FIRM with a `needs-browser-verification` flag — browser rendering may still reject the payload.

**I5 — CSP nonce/hash gate (XSS)**
When a CSP `script-src` with a `nonce-` or `sha256-` directive is present, XSS caps at TENTATIVE — injected scripts require a valid nonce to execute.

## Architecture Overview

```
src/kambo/
├── server.py          # MCP server: list_tools() + _dispatch_tool() registry
├── models.py          # EvidenceChain, Confidence, Phase, Severity, Context
├── validation.py      # 18+ validate_*() functions — evidence graders
├── canary.py          # Orthogonal marker generation + validation
├── calibration.py     # Self-calibration engine (predict vs. actual)
├── pattern_analyzer.py# Tool performance classification
├── learnings.py       # Cross-session JSONL memory store
├── bounty_pricing.py  # Finding value estimation + eligibility gates
├── metrics.py         # SQLite-backed per-tool statistics
├── pipeline.py        # Asset parsers (recon output → Asset objects)
├── scope.py           # Scope validation + pentest-only lock
├── env_loader.py      # Zero-dep .env loader (invoked at startup)
├── config.py          # Pydantic settings wrapper
└── tools/
    ├── recon.py        # Phase 1: DNS, subdomain enum, whois, ASN, certs
    ├── scanning.py     # Phase 2: port scan, web fuzzing, WAF detection
    ├── vulns.py        # Phase 3: SQLi, XSS, SSRF, SSTI, JWT, GraphQL, …
    ├── exploit.py      # Phase 4: RCE, auth bypass, cred extraction
    ├── post_exploit.py # Phase 5: lateral movement, persistence (pentest-only)
    ├── reporting.py    # Phase 6: finding submission, report generation
    ├── api_security.py # OWASP API Top 10 (BOLA, BFLA, resource exhaustion)
    ├── bounty.py       # Bug bounty intel: classify, score, price, timeline
    ├── platforms.py    # HackerOne, Bugcrowd API integration
    ├── cloud.py        # AWS/Azure/GCP enumeration + secret detection
    ├── containers.py   # K8s RBAC, container escape, image scan
    └── ad.py           # Active Directory (pentest-only)
```

### Tool Registry Invariant
`server.py` maintains two synchronized lists: `list_tools()` (what is advertised to the LLM) and `_TOOL_REGISTRY` / `_dispatch_tool()` (what can be called). These must never drift. The `TestToolDispatchConsistency` test enforces this at test time.

### Confidence Threshold Map
| Weight range | Tier       | `confidence_pct` band |
|-------------|------------|----------------------|
| ≥ 2.0       | CONFIRMED  | 85–99%               |
| ≥ 1.0       | FIRM       | 50–79%               |
| > 0.0       | TENTATIVE  | 10–39%               |
| 0.0         | (no signal)| —                    |

### Phase Lifecycle
`RECON → SCANNING → VULN_ANALYSIS → EXPLOITATION → POST_EXPLOITATION → REPORTING`

Each phase is gated by scope validation (`scope.py`). Post-exploitation requires `Context.PENTEST` or `Context.CTF`.

## Known False-Positive Patterns

These patterns consistently produce false positives and are gated in the validators:

- **SPA frameworks** (React, Angular, Vue, Svelte) — virtual DOM intercepts injection, caps XSS at TENTATIVE
- **CSP with nonces** — caps XSS at TENTATIVE (I5)
- **Non-claimable dangling CNAMEs** — AWS ELB/NLB, RDS, ElastiCache endpoints are account-bound; `_non_claimable_resource()` suppresses takeover confidence
- **curl-only XSS reflection** — browser rendering may reject; caps at FIRM with verification flag (I4)
- **OOB token in response body** — reflection, not execution; body-token branch skipped when `oob_hit=True` (I3)
- **Same-org CORS subdomain reflection** — organization controls subdomains; caps at TENTATIVE
- **Category-7 info disclosure without PoC** — acceptance × 0.2 in pricing

## Metrics and Self-Improvement

Each tool records per-run metrics (findings count, confidence distribution, FP rate) in SQLite via `metrics.py`. The improvement loop:

1. `/kambo-hunt` — hunt session, evidence chains grade findings
2. User confirms or rejects findings via `report_confirm_finding`
3. `/kambo-refine` — `pattern_analyzer.py` classifies tools as elite/reliable/noisy/broken
4. `/kambo-calibrate` — `calibration.py` generates weight adjustment recommendations
5. Recommendations reviewed and applied → next session starts with better priors

Learnings from each cycle persist at `~/.kambo/learnings.jsonl` for continuity.
